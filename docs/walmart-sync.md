# Walmart 正式订单同步

店铺管理 → 订单同步 → 启用自动同步。所有店铺从 **2026-10-01 00:00:00 美西标准时间（UTC−8）** 起接收订单，包含当天，即 UTC `2026-10-01T08:00:00Z`；之前的订单不落库、不自动确认。首次拉取从该起点至本轮启动时间，结束时间始终动态取本轮启动时的当前时间。旧店铺起点不同的，在下次同步持有店铺锁后重置扫描游标和核对时间。暂停后恢复保留进度。只读预览也限制在该日期之后，已有历史数据不删除。

每店约 20 分钟同步一次，可点击「立即同步 / 重试」提前执行。后端每 30 秒检查到期任务，按等待时间填充空闲名额；单进程最多同时同步 3 家店铺，手动和自动任务共用上限。同店铺不重入，慢店铺仅占自己的名额，不阻塞其他店铺。超过并发上限时排队，实际间隔受任务耗时影响，不保证精确 20 分钟。认证失败也记录本轮开始时间，避免每 30 秒重复重试。重启依据持久化的上次启动时间判断是否到期。

## 防漏单回查

- 每轮从“上次成功游标减 48 小时”查询，避免平台延迟放单越过旧的 5 分钟回查窗口。
- 每 24 小时从“上次成功游标减 7 天”核对一次；长期停机保留旧游标，不会只查当前时间附近而漏掉停机期间数据。
- 新增 `walmart_sync_states.lastReconciledAt` 可空字段。升级后的旧店铺该值为空，第一次自动从 10 月 1 日补查至本轮开始时间，成功后才记录核对时间；不会每轮全量回查。
- 所有范围下限都不早于接收起点。补查和核对仍按店铺＋客户订单号＋SKU 更新，不覆盖人工采购信息。
- 先拉订单列表，再刷新列表中未覆盖的历史非终态/确认失败订单。同一轮相同 PO 不重复处理。
- 分页失败、订单保存失败或任务暂停时，不推进成功游标和核对时间；下次重试会再次覆盖缺口。已有订单落库后确认失败仍按原回执机制重试。
- 同步弹框显示本轮查询类型及实际起止时间，便于定位空结果和查询范围问题。

48 小时/7 天回查不能保证自动发现无限期延迟的订单；超出范围的异常需要定向补查。此机制不改变平台审核时长，也不能修复店铺密钥认证错误。

## 数据与确认

- 以系统店铺名 `shopName`、Walmart 客户订单号 `customerOrderId`、商品 SKU `item.sku` 三字段查重，重复拉取覆盖同一条记录，不存在时新增。PO 号与商品行号用于平台接口调用及溯源，不参与本地去重。同一响应中重复 SKU 取最后一行，不累加数量；历史已存在多条重复明细时优先更新已绑定相同组合的记录，否则更新最早的一条，不新增也不删除其余旧明细。
- 一个订单的全部商品行及同步回执在同一事务提交后，才调用确认接口。再次 GET 订单检查实时状态，仅所有商品行为 `Created` 的 `SellerFulfilled` 订单调用 `POST /v3/orders/{purchaseOrderId}/acknowledge`。
- 已确认、已发货、已取消、已送达以及 WFS 均不确认。混合状态不使用整单确认接口，标为待核对。
- 确认超时/失败保存原因，下次任务先 GET 远端状态。远端已确认时直接同步状态，不重复 POST。不会因为本地第一次保存后记录已存在而丢失确认重试。
- 确认失败不删除已保存的订单。导入失败不推进创建时间游标，重跑由稳定行键去重。分页和分履约类型查询全部完成后才更新进度。
- 首次范围内已接入的非终态订单会继续逐单刷新，以更新发货、送达、取消等后续状态；不能只依赖按创建时间查询。
- 平台状态保存在 `order_items.walmart`，不覆盖人工维护的内部订单状态、采购状态、采购渠道、采购金额或采购人员。新增明细采购人员绑定启用同步的账号。
- `platformOrderStatus`（平台订单状态）独立列保存中文状态；未知状态保留接口原文，多状态以逗号分隔。`productSpecification`（商品规格）独立 TEXT 列按接口 `groupingAttributes` 顺序提取属性值，以 `, ` 拼接，例如 `Brick red, Card Bag`。平台状态显示在订单列表并可筛选，规格保留在商品折叠详情中，两者参与完整订单导出；商品规格禁止人工修改，采购导入不能映射更新这两个字段。商品接口成功但没有属性时清空旧规格，查询失败则保留原值。
- 变体只读取 `GET /v3/items/{sku}?productIdType=SKU` 返回的 `ItemResponse` 中匹配 SKU 的 `variantGroupInfo.groupingAttributes`，不解析标题。正式同步按店铺＋SKU 复用订单中已保存的成功规格快照，缓存 24 小时；一次任务内按 SKU 去重查询。缓存到期或缺失时重新请求，失败保留原规格和原抓取时间，不延长有效期。预览始终查询最新商品接口，不写缓存。无需 Redis 或新增数据表。
- 列表（含后续分页）和单笔订单查询均传 `incentiveInfo=true`。`orderAmount` 通常为当前商品行 PRODUCT 与 SHIPPING 的 `chargeAmount.amount` 合计；当 `incentive.type` 为 `Walmart funded` 时，以 `incentive.originalPrice.amount × orderLineQuantity.amount` 替换商品金额，再加 SHIPPING（原价为单件价格）。平台出资不扣卖家收入，不额外再加 `walmartFundedIncentive`，税费单独保存，PRODUCT/SHIPPING 已是行金额，不再次乘数量。原价缺失、格式无效或不是 USD 时停止该单保存并报错，避免静默记录优惠价。其他激励（如佣金减免）不按原价恢复。激励详情同时保存在商品平台快照；确认订单的 POST 回执省略激励时，只保留确认前 GET 已核实的同一行（行号＋SKU）激励。履约方直接取 `shipNode.type`，不同于人工采购字段“发货模式”（FBM/FBA）。
- 商品图片保存 Walmart 官方返回的图片 URL，列表、只读商品信息和订单导出共用该字段；不从标题猜测图片或规格。既有图片保留，禁止通过人工编辑或采购导入替换。完整订单导出生成嵌入式缩略图，不把官方图片 URL 改写为采购上传地址。
- 商品数量沿用 `quantity`，取当前商品行 `orderLineQuantity.amount`；新订单首次创建时将采购数量 `purchaseQuantity` 初始化为相同值。后续同步仅更新商品数量，不改采购数量；历史订单的采购数量保持空值，不由同步补齐。
- 出单日期对应接口下单时间 `orderDate`；时间戳原值保存在平台快照，现有 DATEONLY 列按固定 PST（UTC−8）转换。平台详情展示原时间戳转换结果。发货预警仅适用于平台订单状态为“已确认”的明细，行颜色、倒计时、数量统计与预警筛选使用相同范围；截止时间仍为平台发货日期次日北京时间 15:00。

## 预览和运行

### 客户取消申请

商品行的 `intentToCancel`（布尔值 `true` 或字符串 `TRUE`）单独保存到 `order_items.walmart.intentToCancel`。仅当平台订单状态为“已确认”且取消申请标记为 true 时，在订单号旁显示红色“客户申请取消”提示；其他平台状态不提示。不将实际的 `Acknowledged` 状态改成 `Cancelled`，也不会自动取消订单或变更采购状态。后续官方同步返回 FALSE 或不再返回该标记时，提示随最新响应消失。原始取消意向标记仍按平台返回值保存。

“客户取消申请”筛选与红色提示共用口径：“客户申请取消”仅包含平台状态为“已确认”且意向标记为 true 的明细；“无取消申请提示”包含其余状态（含空状态）或未标记取消意向的明细，不表示平台保证没有取消申请。点击查询后生效，分页、统计和导出沿用该条件及账号数据权限。

升级时通过 `npm run db:migrate` 分批从现有官方订单回执补齐缺失标记，严格按店铺、PO、商品行号及 SKU 匹配；已有标记不覆盖，无匹配回执的留待后续同步。不新增表或列，不重新拉取平台订单，不触发确认或取消接口。

预览只读取平台数据，不新增订单、回执或确认任务。选定范围最多 31 天、200 个订单。前端选择器使用浏览器时区，发送带时区的 ISO 时间给后端。

同步任务结果、失败原因和待核对订单在店铺同步弹框显示。MySQL 命名锁防止多个进程同时处理同一店铺。并发上限按单进程计算，当前生产部署为单容器单进程；若未来扩展多副本，需要增加全局限流。单店内订单分页和确认仍按顺序执行，保留 429 退避及写接口不盲重试。暂停不撤回已经发出的 API 请求，当前请求完成后停止后续处理。

部署前先运行 `npm run db:migrate`，本次为同步表新增可空的 `lastReconciledAt`；其他既有迁移保持幂等，不重建业务表。先迁移再重启后端。每个店铺需要分别启用；密钥不进入同步接口返回、回执或错误日志。

## 验证

### Walmart 资助金额历史修复

2026-10-24 核对 MY-L-16 的客户订单 `200015410440051`：PRODUCT 为 49.59，SHIPPING 为 25.99；开启激励查询后返回 `type: "Walmart funded"`、`originalPrice: 55.09 USD`、`walmartFundedIncentive: -5.50 USD`。正确不含税订单金额是 **81.08**，旧金额为 75.58。

先发布新同步逻辑、备份数据库，再运行独立脚本。该脚本不接入启动迁移，避免部署健康检查等待远端 API。默认只读预览，输出 JSONL 形式的店铺、客户订单号、SKU、修改前后金额和价格系数；不输出密钥或客户地址。

```bash
# 在项目根目录预览指定订单；Docker 中工作目录为 /app。
node backend/scripts/repair-walmart-incentives.js --store MY-L-16 --order 200015410440051
# 检查预览后应用同一范围
node backend/scripts/repair-walmart-incentives.js --store MY-L-16 --order 200015410440051 --apply
# 不传 store/order 则核对全部店铺已有订单（含已送达/取消的历史单）
node backend/scripts/repair-walmart-incentives.js
node backend/scripts/repair-walmart-incentives.js --apply
```

生产环境可以用 `docker exec -w /app my-order node backend/scripts/repair-walmart-incentives.js ...` 执行，并将输出保存在本次发布备份目录。预览与应用各自重新 GET 官方订单，应用以当时最新响应为准。按店铺串行、每批读取100条已有回执，复用已有请求超时和限流退避；不新增订单、不调用确认或取消接口。

修复与正常同步共用店铺命名锁，忙碌店铺跳过后可重试。仅修正三字段唯一匹配且店铺ID、PO、商品行号绑定一致的 Walmart 资助明细；事务内更新订单金额、对应价格系数和激励快照/回执激励字段，不覆盖采购备注、状态、渠道、采购数量、税费或其他业务字段。重复执行不会重复加价。失败或跳过返回非零退出码并保留原因；部分成功可重跑。首页、店铺销售统计和导出使用数据库订单金额，修复后刷新即采用新值。该流程无需新增数据库字段、依赖或消息队列。

## 订单管理的退货退款（2026-11-04，本地完成）

- 订单列表新增只读“退货退款状态”列、多选筛选，状态包括申请中、退款处理中、已退款、已取消、状态待核实。与平台订单发货状态分别展示，不改采购状态、是否售后等人工字段。
- 读取 `GET /v3/returns`，依据 `customerOrderId`、明细 `item.sku`、`purchaseOrderId` 与店铺关联。按退货单号＋退货行保留多笔记录，仅标记实际涉及的商品；同一商品多笔退货可同时呈现不同状态。退货 COMPLETED 不代表 REFUND_COMPLETED；未知状态保留原值并显示状态待核实。
- 展开商品详情展示接口退货单号、商品行、数量、申请时间、退款状态/退货状态、原因、行金额及退款完成时间。时间为固定 PST；金额使用含税 lineTotal，未完成退款的金额不宣称已到账，缺失不作零。完成时间取已完成退款事件，取消或处理中不展示旧完成时间。
- 纳入原每20分钟订单同步任务，共用店铺命名锁和最多3店并发。先同步普通订单，再读取退货退款。首次从2026-10-01 00:00 PST查询修改记录，此后从上次成功游标回溯48小时；按7天切窗口、每页50条、单轮最多100页，校验分页完整性与重复游标。未筛选WFS或退款状态。
- 退款接口失败独立记入同步结果，保留已有退款快照、不推进退款游标，不影响已完成的普通订单进度。店铺同步弹窗展示错误及未关联记录；普通页面刷新只查询数据库，不直接请求Walmart。
- 原订单未在系统时，使用该退货行PO调用官方订单详情，核对客户订单号，仅接收2026-10-01 00:00 PST至同步开始时刻的原订单；复用原入库匹配，不重复创建、不覆盖人工采购字段。补拉路径不确认订单，也不执行任何退款操作。范围外行跳过并在本轮结果计数。
- 业务键重复或PO不一致不猜测匹配；请求失败及未匹配记录持久化后重试。每轮最多补拉50个原订单，另重试最早100条待关联退货记录，避免无界网络请求。
- 增量迁移新增 `walmart_return_records`（店铺＋退货单唯一，店铺＋客户订单号/待关联索引），`order_items.returnInfo` JSON，及同步表可空 `returnsCursorAt`、`returnsCredentialKey`。新字段不加入人工编辑/采购导入元数据；独立于普通订单 `walmart` 快照，不因普通同步被抹掉，也不增加人工编辑版本。密钥变化后重新查询并清除旧凭据的退款摘要。
- 查询和两类导出共用筛选，状态同框取并集、其他条件取交集；完整订单导出增加退货退款状态列。沿用运营店铺权限和WFS人工只读，表头选择与排序按账号保存。无需新增Redis、消息队列或依赖。
- 本地验证：3项解析/分页单元测试、7项独立MySQL库集成测试及19项原Walmart同步测试通过；包括重复同步、部分商品、多笔退货、补拉、范围边界、失败重试、WFS、账号权限、两类导出、只读、迁移幂等。前端构建及Playwright页面验证通过。
- 本地用MYZ-L-104只读查询取得25个退货单，随后仅在本地补拉并关联14条符合范围的已退款商品明细。该店本地自动同步保持关闭；服务器未发布。接口样本验证不能保证没有退货记录的所有退款场景都被此接口覆盖。

官方参考：[Returns接口](https://developer.walmart.com/us-marketplace/reference/getreturns)、[退货单及退款明细字段](https://developer.walmart.com/us-marketplace/docs/retrieve-return-orders)。
