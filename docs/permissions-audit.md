# 角色权限与操作日志

## 权限范围

- 最高管理员：全部菜单、全部订单和全部日志。
- 主管：除账号管理、采购渠道维护、采购状态维护外的全部菜单，全部店铺数据及金额，全部账号日志和导入结果；保留订单采购渠道分配、采购状态修改和售后供应商反馈权限。
- 采购：订单管理、导入采购、导入模板、操作日志、采购渠道/平台/状态维护；可查看和操作全部店铺订单。
- 运营：订单管理、导入采购、导入模板、操作日志、风险地址、运营订单状态维护；订单数据仅限店铺管理中 `ownerId` 为本人账号的店铺。
- 采购状态修改、单条及批量分配采购渠道向管理员、主管和采购开放。运营可查看和筛选，但编辑时这两个字段只读，相关操作按钮隐藏；后端同时拒绝修改或清空，运营订单状态及其他已有权限不变。
- 导入模板共享维护。采购、运营仅能查看自己的日志和导入结果。
- 四个角色均可使用采购售后。管理员、主管、采购处理全部店铺工单，运营只处理本人店铺；有权限者均可创建、回复、完毕和重新打开。标记已反馈供应商限管理员、主管和采购。WFS 不允许写工单；工单与记录不可修改或删除，旧记录不进入两个月日志清理。详见 [采购售后](purchase-after-sales.md)。
- 四个角色均可查看“采购统计汇总”，管理员、主管、采购查看全部店铺，运营按当前所属店铺筛选历史快照；页面、渠道选项和整体汇总均遵守此范围。只读，不提供手动生成或修改历史报表接口。详见 [采购统计](purchase-statistics.md)。
- 店铺管理将一家店铺绑定到一个账号，一个账号可绑定多家店铺；运营的订单范围以此绑定为准。表头显示与拖动顺序独立保存到当前账号，不影响共享模板或其他账号配置。
- 既有 WFS 人工只读、禁止手工新增和删除订单、采购导入只更新唯一匹配订单等限制继续生效。

菜单过滤、路由守卫和后端接口白名单同时实施。运营的数据范围作为数据库查询的额外 AND 条件，覆盖列表、预警统计、详情、两类导出和所有人工写入。未绑定店铺、不存在的店铺及无所属店铺账号均不会回退到全量数据。账号角色每次请求读取数据库；店铺归属在写入事务中再次校验。

导入预览跳过其他店铺的行，反馈原文件中的店铺、订单号、SKU、行号及原因，不返回其他店铺的数据库明细。提交时重新校验店铺归属，已失去权限的行继续跳过。生成预览只允许上传者使用自己的文件；Excel 检查允许上传者、管理员和主管查看。管理员、主管和原创建人可查看导入结果，提交仍须由原创建人完成。

运营采购导入忽略采购状态映射并提示，其他有效字段继续更新；仅包含采购状态的行跳过。提交旧预览时再次检查当前角色，不能绕过限制。采购渠道继续不参与任何账号的采购导入；共享模板仍可保留采购状态映射供管理员、主管和采购使用。

## 日志与保留策略

首页向四个角色开放；运营只能查看所属店铺，管理员、主管、采购可查看全部店铺及金额。权限由 `/api/home` 服务端校验，快照采集和首页读取不写操作日志。详见 [首页统计](home-dashboard.md)。

操作日志沿用 `audit_logs` 表，记录账号主动发起的新增、修改、删除、导入、导出及登录等操作，包括账号、时间、请求结果和字段变化。修改日志与业务事务一同提交或回滚；操作请求摘要在响应结束时异步写入，写入失败会输出服务端错误日志。进程异常退出可能丢失尚未落库的请求摘要，已提交业务事务中的字段日志不受影响。

密码、密码摘要、Client ID、Client Secret、会话和令牌不保存明文。整份导入 JSON 和 Walmart 原始快照不复制到日志；字段长文本最多保留 12000 字符。旧日志无法追溯补齐此前未记录的字段值。

按北京时间回退两个自然月（月底取目标月最后一天），日志查询即时排除过期记录。服务启动和每小时自动清理，每批最多 1000 条、每轮最多 10 批，避免长事务；若历史积压超过一轮上限，后续轮次继续清理。保留当前月对应日、时分秒之后的最近两个月日志，并非按整月清空。

日志及导入结果界面只读，任何账号（包含管理员）均无日志增删改接口。导入报告、订单、图片和账号等业务记录不属于日志清理对象。导入提交只能在导入采购页面完成。

查询、查看详情、翻页、刷新及轮询均不再生成日志，失败的查看请求也不记录。Walmart 预览和同步（手动或定时）不生成请求或入库变更日志；账号主动修改同步开关配置仍属于配置修改，正常记录。已有历史查询和同步日志不主动删除，沿用两个月保留规则。同步状态与错误仍可在店铺同步结果中查看。

## 数据库与验证

运行 `npm run db:migrate` 增量添加日志时间/账号/操作索引、导入创建人时间索引和订单店铺日期索引。主管角色迁移仅在 `users.role` 原 ENUM 末尾追加 `supervisor`，保留已有账号、角色和业务数据，重复执行不再修改列；初始化及正式迁移脚本均已接入。沿用 Express、Sequelize 和 MySQL，无新增 Redis、队列或 npm 依赖。

独立临时数据库验证：

```powershell
$env:DB_NAME = 'my_order_permissions_test_' + [DateTimeOffset]::UtcNow.ToUnixTimeMilliseconds()
node --test backend/test/permissions-audit-integration.test.js
Remove-Item Env:DB_NAME
```

测试只有数据库名匹配 `my_order_permissions_test_数字` 才执行，结束后仅删除该一次性数据库。已有业务库不参与测试。

主管专项测试使用 `my_order_supervisor_test_数字` 与 `node --test backend/test/supervisor-integration.test.js`；前后端角色矩阵使用 `node --test backend/test/role-permissions.test.js`。专项覆盖旧账号迁移、禁用接口防绕过、全店数据及导出、渠道/状态操作、跨店导入、全账号日志与结果、售后反馈、WFS保护和会话角色即时生效；禁用真实企业微信推送。
